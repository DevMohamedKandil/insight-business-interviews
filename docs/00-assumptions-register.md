# InsightAI — Assumptions Register

**Purpose:** A single, running source of truth for every assumption made across the 20 planning documents. Assumptions are not hidden inside prose — they are logged here, cross-referenced to the document that made them, so a future architect, investor, or engineer can find and challenge every one of them without re-reading everything.

**Format:** Each entry states the assumption, why it was made (rationale), what happens if it turns out false (impact), and which document it lives in.

| A1 | The founder is the sole Admin Panel user for the entire v1 lifetime. | Confirmed explicitly by founder (2026-07-31) when asked to choose between single-operator and multi-tenant SaaS scope. Avoids building tenant isolation, billing, and multi-user auth before there's a second user to justify it. | Multi-tenancy becomes a scoped, deliberate migration (schema + security rules + admin auth all change) rather than a retrofit surprise — tracked explicitly in Document 12 (Roadmap) as a future phase, not silently absent. | [01](./01-vision-document.md) §13.5 |
| A2 | At least one of OpenAI / Claude / Gemini will always have a valid, funded API key present in the deployment environment. | The system has no defined behavior for "zero configured providers" — this is treated as a deployment/ops precondition, not a runtime case the code must handle gracefully. | If all provider keys are simultaneously invalid/expired, every interview turn fails. | A3 | Early v1 respondent volume is low (dozens to low hundreds of interviews), so even non-optimal cost paths stay financially negligible. | Realistic expectation for a pre-launch internal research tool with no marketing yet. | If a template is shared to a large audience faster than expected (e.g., a viral link), the daily spend cap (A-required in PRD FR-2) is the actual safety net — this assumption affects *urgency* of optimization work, not *correctness* of the cap mechanism, which is mandatory regardless of volume. | [02](./02-prd.md) §7 |
| A4 | Firestore's per-document 1 MiB size limit and ~1 write/second sustained-write-rate-per-document guidance are never approached by any single document in this schema. | Messages, sessions, and rollups are all designed to be small, bounded documents (Document 5) — no unbounded arrays. | If a template's coverage-goal list or a session's message count grows unusually large, a poorly-designed document (e.g., embedding all messages inside one session doc) would hit this limit. Mitigated by design: messages are a subcollection, never an embedded array (Document 5 §3). | [04](./04-database-design.md), [05](./05-firestore-collections.md) |

Should be monitored explicitly in the Admin Dashboard (blocked-by-AppCheck counter) from launch. | [06](./06-security-model.md) |
| A6 | A single Firestore region, single Cloud Functions region, no multi-region setup, is sufficient for v1 and the medium-term roadmap. | Respondents are expected to be geographically concentrated (Egypt/MENA-focused personas per Vision §5) in the near term; multi-region adds cost and complexity with no near-term latency benefit. | If respondent geography broadens significantly and latency complaints emerge, Document 17 (Scaling Strategy) defines the explicit trigger conditions and migration path for going multi-region. | [03](./03-software-architecture.md) §9, [17](./17-scaling-strategy.md) |
| A7 | Top-20 bounded maps (countries, occupations, pain points, etc.) are sufficient granularity for dashboard rollups. | Matches typical long-tail distribution of these categories; showing beyond top-20 in a dashboard chart has diminishing UX value regardless of data completeness. | If deep long-tail analysis is needed later, the raw `sessions`/`messages` collections remain queryable as a fallback — this is a dashboard-convenience bound, not a data-loss risk. | [05](./05-firestore-collections.md) §6 |
| A8 | `synthesisReports` document ID = `sessionId` is an acceptable one-to-one constraint (a session can never need more than one synthesis report). | Matches PRD FR-22 exactly ("synthesis runs once per completed session"). | If a future requirement needs re-synthesis with different parameters, this becomes a versioned subcollection under the report (same pattern as templates §1.1) — additive, not breaking. | [05](./05-firestore-collections.md) §3 |
| A9 | Regex/pattern-based PII masking catches common structured cases (phone numbers, emails, ID numbers) but is not exhaustive against free-text-described identifying detail. | Building an ML-based PII detector is disproportionate engineering effort for v1 scale; even large-scale products don't fully solve this. | If a sensitive-disclosure incident occurs, response is manual review + rule refinement, not a claim that masking is complete. Tracked in Document 15 (Technical Risks). | [06](./06-security-model.md) §7 |
| A10 | The check-then-call spend-cap race condition will not produce a materially damaging overshoot at realistic v1 concurrency. | Full transactional atomicity around an external API call is a Firestore anti-pattern (transactions must not wrap slow external I/O) and would hurt latency for a currently-negligible risk. | If traffic concentration makes concurrent-request races common on one template, this must be revisited — explicit, not silent. | [06](./06-security-model.md) §4 |
| A11 | Development capacity is roughly one focused engineer (possibly AI-paired), justifying 1-week sprints instead of conventional 2-week sprints. | Shorter sprints surface wrong assumptions faster at solo/small-team velocity; sizing should match actual team size, not copy larger-team convention. | If a team is hired, sprint length should be revisited against the new capacity/coordination profile. | [13](./13-sprint-plan.md) §1 |
| A12 | Firebase free-tier quotas and LLM per-token pricing quoted in Document 16 remain directionally accurate; exact figures are re-verified before major scaling/funding decisions. | Both Google's and AI providers' pricing pages change over time; a planning document is a snapshot, not a live feed. | Relative conclusions (which provider is cheaper, roughly how many sessions fit in a cap) likely still hold even if absolute numbers drift — but must not be quoted to a third party without re-verification. | [16](./16-cost-estimation.md) §1 |
